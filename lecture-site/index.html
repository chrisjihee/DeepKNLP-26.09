언어모델의 발전 과정

무엇이 문제였고 무엇으로 풀었는가 — Word2Vec에서 LoRA까지

분산 표상과 순환 신경망 — 단어를 벡터로 바꾸기

초기 NLP는 단어를 one-hot 기호로 다뤄서 '영화'와 '드라마'가 서로 무관한 벡터였다. Word2Vec(2013)은 주변 단어로 단어를 예측하게 학습해 의미가 가까운 단어를 가까운 벡터로 만들었고, RNN/LSTM은 이 벡터들을 순서대로 읽어 문장 단위 문맥을 담았다. 다만 단어마다 벡터가 하나로 고정되고, 계산이 순차적이라는 한계가 남았다.

무엇을 — 단어를 저차원 실수 벡터(분산 표상, distributed representation)로 바꾸고, 그 벡터열을 순환 신경망으로 읽어 문맥을 인코딩하는 단계다. 대표 연구는 Word2Vec(Mikolov et al., 2013)과 GloVe(2014), 그리고 LSTM(1997)·GRU(2014) 계열의 순환망이다.

왜 — one-hot 표현에서는 어휘 크기만큼 차원이 커지고 임의의 두 단어의 내적이 항상 0이다. 즉 '재미있다'와 '즐겁다'의 유사성을 모델이 알 방법이 없다. 분포 가설(비슷한 문맥에 등장하는 단어는 비슷한 의미를 갖는다)을 학습 목표로 바꾼 것이 Word2Vec이다.

어떻게 — CBOW/Skip-gram으로 주변 단어 예측 문제를 풀면 부산물로 단어 벡터가 얻어진다. 문장 분류라면 그 벡터열을 LSTM에 넣고 마지막 은닉 상태를 분류기에 연결하는 식이었다.

남은 문제는 두 가지다.

  • 정적 표상: '배'가 신체·과일·선박 중 무엇이든 벡터가 하나였다. 문맥에 따라 표상이 달라져야 한다는 요구가 ELMo(2018) 이후 사전학습 언어모델로 이어진다.
  • 순차 계산: t번째 은닉 상태를 구하려면 t-1을 먼저 구해야 해서 GPU 병렬화가 막히고, 멀리 떨어진 두 단어 사이 정보 경로가 길어 기울기가 소실된다.

참고로 지금 실습에서 이 단계는 코드에 직접 등장하지 않는다. 우리가 쓰는 AutoTokenizer의 서브워드 임베딩이 이 계보의 현재 형태라고 보면 된다.

Seq2Seq의 병목과 어텐션(Attention)

기계번역을 위해 인코더-디코더 구조(Seq2Seq, 2014)가 제안됐지만, 입력 문장 전체를 고정 길이 벡터 하나로 압축해야 해서 문장이 길어질수록 성능이 떨어졌다. 어텐션은 디코더가 매 출력 단어마다 인코더의 모든 위치를 다시 조회해 필요한 곳에 가중치를 주도록 했다. 이 '필요한 곳을 골라 본다'는 아이디어가 이후 모든 구조의 핵심 부품이 된다.

무엇을 — Seq2Seq(Sutskever et al., 2014; Cho et al., 2014)는 인코더 RNN이 입력 문장을 벡터로 요약하고 디코더 RNN이 그 벡터에서 출력 문장을 생성하는 구조다. 어텐션(Bahdanau et al., 2015; Luong et al., 2015)은 여기에 '조회' 단계를 추가한다.

왜 — 입력이 30단어든 100단어든 고정 크기 벡터 하나에 다 담아야 하는 정보 병목(bottleneck)이 있었다. 실제로 문장 길이가 길어질수록 번역 품질이 급격히 떨어지는 현상이 보고됐다.

어떻게 — 디코더의 현재 상태를 질의(query)로 삼아 인코더의 각 위치 상태(key/value)와 유사도를 계산하고, softmax로 정규화한 가중치로 가중합을 만든다. 개념적으로는 세 줄이다.

score_i = f(decoder_state, encoder_state_i)
alpha   = softmax(score)
context = sum_i alpha_i * encoder_state_i

부수 효과 — 어텐션 가중치를 시각화하면 어떤 입력 단어를 보고 어떤 출력 단어를 냈는지 대략 읽을 수 있어, 해석 가능성 측면에서도 주목받았다. 다만 이 시점까지 어텐션은 어디까지나 RNN에 덧붙인 보조 장치였고, 순차 계산이라는 근본 제약은 그대로였다.

Transformer(2017) — 순환 구조를 걷어내다

"Attention Is All You Need"(Vaswani et al., 2017)는 RNN을 없애고 self-attention만으로 인코더-디코더를 구성했다. 모든 토큰이 한 번에 서로를 참조하므로 시퀀스 전체를 병렬로 계산할 수 있고, 임의의 두 토큰 사이 경로 길이가 상수가 된다. 지금 실습에서 쓰는 Hugging Face transformers의 모든 모델이 이 구조 위에 있다.

무엇을 — self-attention(같은 시퀀스 안에서 서로를 조회), multi-head attention(여러 부분 공간에서 병렬로 조회), position-wise feed-forward, residual connection + layer normalization, 그리고 순서 정보를 넣기 위한 positional encoding으로 이루어진 블록을 쌓은 구조다.

왜 — 어텐션이 이미 좋은 성능을 내고 있었다면, 순차 계산이라는 병목을 안고 가는 RNN을 굳이 유지할 이유가 있는가라는 질문이었다. 두 가지가 동시에 해결된다.

  • 병렬화: 한 층의 모든 위치를 행렬곱 한 번으로 계산한다. GPU 활용률이 크게 올라가 학습 규모를 키울 수 있게 됐다.
  • 경로 길이: RNN에서 거리 n인 두 토큰의 정보 경로는 O(n)이지만, self-attention에서는 O(1)이다.

대가 — 시퀀스 길이 n에 대해 어텐션 계산량이 O(n²)이다. 그래서 최대 입력 길이를 제한하는 하이퍼파라미터가 늘 따라다닌다. 실습에서는 이것이 --max_seq_length 512로 나타나고, 긴 문서를 다루는 KorQuAD 추출형 QA에서는 문서를 겹치며 잘라 넣는 --doc_stride 128이 함께 등장한다.

python task4A-qa-ext/train_qa.py \
  --model_name_or_path klue/bert-base \
  --max_seq_length 512 \
  --doc_stride 128

어떻게 이어지는가 — 이 블록을 인코더만 쓰면 BERT, 디코더만 쓰면 GPT, 둘 다 쓰면 T5가 된다. 다음 카드의 세 갈래가 그것이다.

사전학습–파인튜닝 시대: 인코더 / 디코더 / 인코더-디코더

2018년 전후로 대량의 raw 텍스트에 자기지도 학습을 먼저 하고(사전학습), 소량의 라벨 데이터로 태스크에 맞추는(파인튜닝) 방식이 표준이 됐다. BERT는 양방향 인코더로 이해 태스크를, GPT는 단방향 디코더로 생성 태스크를, T5는 인코더-디코더로 모든 태스크를 text-to-text로 다룬다. 이 세 갈래가 실습 저장소의 태스크 구성과 그대로 대응한다.

무엇을 — BERT(Devlin et al., 2018)는 문장의 일부 토큰을 가리고 맞히는 MLM으로 양방향 문맥을 학습한다. GPT(Radford et al., 2018)는 다음 토큰 예측이라는 단일 목표로 학습한다. ELECTRA(2020)는 마스크 복원 대신 '치환된 토큰 판별'로 학습 효율을 높였고, T5(Raffel et al., 2019)는 분류든 QA든 전부 입력 텍스트 → 출력 텍스트로 통일했다.

왜 — 라벨 데이터는 비싸고 raw 텍스트는 싸다. 언어에 대한 일반 지식을 먼저 쌓아 두면 태스크별 라벨은 훨씬 적게 써도 된다는 것이 이 시기의 핵심 발견이다.

대형화, In-context learning, 그리고 효율적 적응

GPT-3(2020)는 파라미터를 키우자 파인튜닝 없이 프롬프트의 예시만으로 태스크를 수행하는 in-context learning이 나타남을 보였다. 다만 사전학습 목표(다음 토큰 예측)와 사용자가 원하는 것(지시 이행) 사이 간극이 남아 instruction tuning과 RLHF가 등장했고, 전체 파인튜닝의 비용 문제는 LoRA 같은 효율적 적응 기법으로 대응한다. 2일차 실습5가 정확히 이 지점이다.

대형화와 in-context learning — GPT-2(2019), GPT-3(Brown et al., 2020, 175B)로 규모가 커지면서 가중치를 갱신하지 않고 프롬프트 안에 예시 몇 개를 넣는 것만으로 태스크가 수행됐다. 성능이 모델 크기·데이터·연산량에 대해 예측 가능한 곡선을 그린다는 scaling law(Kaplan et al., 2020; Hoffmann et al., 2022)가 이 흐름을 뒷받침했다. 규모 감각은 2일차 실습5에서 확인할 수 있다. task5-llm-ft/train.py는 --model만 바꾸면 어떤 디코더 모델이든 같은 코드로 학습한다. 강사가 미리 돌려 둔 스윕은 EXAONE-4.0-1.2B부터 gpt-oss-20B(MoE)까지 아홉 모델이고, 같은 학습셋·같은 평가셋·같은 채점을 썼다(task5-llm-ft/sweep.sh).

python task5-llm-ft/train.py --data data/llm-ft/train_main.jsonl
python task5-llm-ft/train.py --data data/llm-ft/train_main.jsonl --model Qwen/Qwen3.5-2B --out output/llm-ft-qwen35-2b

지시를 따르게 만들기 — 다음 토큰 예측만 학습한 모델은 질문을 받으면 답 대신 비슷한 질문을 이어 쓰기도 한다. 여러 태스크를 자연어 지시문 형태로 바꿔 학습시키는 instruction tuning(FLAN, T0, 2021)이 미학습 태스크로의 일반화를 끌어올렸고, 사람 선호 비교 데이터로 보상모델을 학습해 정렬하는 RLHF(InstructGPT, Ouyang et al., 2022)가 뒤를 이었다. 최근에는 선호 데이터를 직접 쓰는 DPO 같은 단순화된 방법도 널리 쓰인다.

효율적 적응(PEFT) — 수십억 파라미터를 태스크마다 전부 복사해 파인튜닝하는 것은 저장·메모리 양쪽에서 부담이다. LoRA(Hu et al., 2021)는 원 가중치를 얼려 두고 저랭크 행렬 두 개만 학습해, 학습 대상 파라미터를 크게 줄이면서 태스크별 어댑터를 가볍게 교체할 수 있게 한다.

2일차 실습과의 연결 — 1일차에는 태스크마다 모델을 따로 파인튜닝한다(주제분류용 하나, 문장유사도용 하나, 개체명인식용 하나). 2일차 오전의 기계독해도 추출형·생성형으로 하나씩 더 만든다. 2일차 실습5에서는 모델을 하나로 두고 여섯 태스크(주제분류·개체명인식·기계독해·문장유사도·SQL생성, 그리고 보너스인 수학추론)를 지시문 형태로 통일해 LoRA로 함께 학습시킨다. 즉 이 카드에서 훑은 instruction tuning과 효율적 적응을 직접 손으로 확인하는 순서다. 코드는 task5-llm-ft/에 있고, 같은 데이터·같은 평가셋·같은 채점으로 학습한 BERT(인코더)·T5(인코더-디코더) 기준선과 나란히 놓는다. 1일차에는 인코더와 인코더-디코더 둘을 손으로 만들어 보고, 디코더는 2일차 오후에 처음 만난다. 세 구조를 한 표에 세우는 것이 이번 과정의 뼈대다.

언어모델 기반 자연어처리 원리

사전학습·미세조정, BERT의 head 방식, GPT의 생성 방식, 그리고 LLM 프롬프트 방식의 차이

사전학습과 미세조정 — from_pretrained 한 줄이 나누는 두 단계

사전학습은 라벨 없는 대량 텍스트로 언어 표현을 미리 학습해 두는 단계이고, 미세조정은 그 가중치에서 출발해 소량의 라벨 데이터로 목표 태스크에 맞추는 단계다. 실습 코드에서 이 경계는 tokenizer와 model을 from_pretrained로 불러오는 대목에 드러난다.

실습의 모든 태스크가 같은 형태로 시작한다. 1일차 세 노트북이 쓰는 모델 이름은 day1/lab_common.py에 두 줄로 모여 있다.

MODEL_BERT = "klue/roberta-base"          # 인코더. 한국어 RoBERTa (약 110M 파라미터)
MODEL_T5 = "paust/pko-t5-base"            # 인코더-디코더. 한국어 T5 (약 275M 파라미터)

노트북은 이 이름 하나를 tokenizer와 model에 각각 넘긴다. 개체명인식 노트북의 build_model은 미션이 아니라 그대로 주어지는 코드다(day1/03_개체명인식.ipynb).

tokenizer = L.load_bert_tokenizer(MODEL)

def build_model():
    return AutoModelForTokenClassification.from_pretrained(
        MODEL, num_labels=len(L.BIO_LABELS),
        id2label=dict(enumerate(L.BIO_LABELS)), label2id=L.BIO2ID)

from_pretrained가 하는 일은 세 가지로 갈린다.

  • config: 모델 구조 정의. from_pretrained에 num_labels를 넘기는 순간 이 모델이 풀 태스크가 결정된다.
  • tokenizer: 사전학습 때 쓰던 어휘·분절 규칙. 모델과 반드시 짝이 맞아야 한다.
  • model: 사전학습된 가중치 + 태스크용 head. head 가중치는 사전학습 체크포인트에 없으므로 새로 초기화된다. 미세조정이 학습하는 것은 (동결하지 않는 한) 몸통과 head 양쪽이다.

실습별로 어떤 사전학습 모델을 기본값으로 쓰는지는 다음과 같다.

인코더(BERT) 계열 — 몸통은 그대로, head만 갈아끼운다

BERT류 인코더는 문장을 토큰별 벡터로 바꿔주는 데까지만 담당하고, 그 벡터를 어떤 정답 공간으로 사상할지는 위에 붙는 head가 정한다. 1일차 세 노트북은 몸통이 같아도 위에 붙이는 head가 서로 다르다 — 라벨 7개짜리 분류, 출력 하나짜리 회귀, 토큰마다 BIO 태그.

같은 인코더에 어떤 head를 붙였는지가 태스크를 결정한다. 저장소의 실제 코드에서 확인할 수 있다.

태스크모델 클래스head 출력정답 형태
주제분류 (1일차 실습1)AutoModelForSequenceClassification문장당 7개 로짓라벨 문자열 (TC_LABELS 7종)
문장유사도 (1일차 실습2)AutoModelForSequenceClassification (num_labels=1, problem_type="regression")문장 쌍당 실수 1개0.0~5.0 점수 (float)
개체명인식 (1일차 실습3)AutoModelForTokenClassification토큰당 13개 로짓BIO 태그열 (["O"] + B-* + I-*)
추출형 QA (2일차 실습4A)AutoModelForQuestionAnswering토큰당 start/end 로짓 2벌start_positions, end_positions 정수

개체명인식의 13은 개체 유형 6종에서 자동으로 만들어진다. day1/lab_common.py가 이렇게 조립한다.

# NER_LABELS = {"PS": "사람", "LC": "지역", "OG": "기관", "DT": "날짜", "TI": "시간", "QT": "수량"}
BIO_LABELS = ["O"] + [f"{p}-{t}" for t in NER_LABELS for p in ("B", "I")]   # 1 + 6×2 = 13
BIO2ID = {label: i for i, label in enumerate(BIO_LABELS)}

예측을 뽑는 방식도 head 모양을 그대로 따라간다. lab_common.predict_choice는 문장 단위로 logits.argmax(-1)를 해 라벨 문자열을 돌려주고, predict_ner도 argmax(-1)이지만 토큰 축이 하나 더 있어 토큰마다 태그가 나온다. 문장유사도는 argmax가 아예 없다 — 출력이 하나뿐이라 그 값을 0~5로 자르기만 한다(predict_sts). 추출형 QA는 argmax 한 번으로 끝나지 않고 start/end 조합에서 원문 span을 복원하는 후처리(lab_common.postprocess_mrc)가 따로 필요하다.

즉 인코더는 "의미를 벡터로 만드는 부품"이고, 태스크는 그 위에서 결정된다.

그래서 BERT는 태스크마다 모델이 따로 생긴다

head의 출력 차원이 그 태스크의 라벨 공간에 고정되기 때문에, 학습이 끝나면 태스크 수만큼 별개의 체크포인트가 남는다. 1일차에 노트북을 세 번 돌리는 이유가 그것이다.

이 섹션에서 가장 중요한 지점이다. 왜 태스크마다 모델을 따로 만들어야 했는가?

  • 출력 차원이 다르다. 주제분류 head는 7차원, 문장유사도 head는 1차원, 개체명인식 head는 13차원, 기계독해 head는 (start, end) 2벌이다. 서로 형태가 달라 가중치를 그대로 옮겨 쓸 수 없다.
  • 손실 계산 단위가 다르다. 주제분류는 문장 하나에 라벨 하나, 문장유사도는 문장 쌍 하나에 실수 하나(MSE), 개체명인식은 토큰마다 라벨 하나(특수 토큰은 -100으로 손실에서 뺀다), 기계독해는 정답 시작·끝 위치 두 개다.
  • 평가 지표도 다르다. 주제분류는 정확도, 문장유사도는 피어슨 상관, 개체명인식은 개체 단위 F1, 기계독해는 EM/F1이다. 채점 함수 자체는 task5-llm-ft/common.py의 score_task 하나에 모여 있다.

그 결과가 실습의 모양이다. 1일차 오후에 노트북을 세 번 돌리고, 결과 파일도 태스크마다 따로 쌓인다(output/day1/tc-bert.json·sts-bert.json·ner-bert.json).

디코더/seq2seq — 답을 골라내지 않고 써낸다

GPT류 디코더와 T5류 seq2seq는 출력이 항상 토큰 시퀀스여서, 태스크가 바뀌어도 모델 구조는 그대로다. 대신 정답을 문자열로 생성하므로 추출형만큼 정확하지 않을 수 있다.

T5류 seq2seq와 GPT 계열 디코더는 출력층이 어휘 크기만큼의 다음 토큰 예측기 하나다. 태스크별 분류기가 아니므로 태스크가 바뀌어도 이 head는 바뀌지 않는다. 1일차 세 노트북의 T5 파트가 이미 그렇다 — 주제분류·문장유사도·개체명인식에서 AutoModelForSeq2SeqLM 하나를 그대로 쓰고, 바뀌는 것은 입력에 적어 주는 지시문과 정답 문자열뿐이다(day1/lab_common.py의 load_t5·encode_t5).

2일차 실습4B는 같은 아이디어를 기계독해에 적용한 경우다. 정답 span의 위치를 맞히는 대신 정답 문자열 자체를 생성한다(task4B-qa-gen/train_qa_seq2seq.py).

targets = [answer["text"][0] if len(answer["text"]) > 0 else "" for answer in answers]
labels  = tokenizer(text_target=targets, max_length=max_answer_length, ...)

같은 KorQuAD 데이터로 같은 조건(train-half.jsonl, 1 epoch)에서 학습한 두 방식의 기록이 스크립트 주석에 남아 있다.

방식모델EMF1
추출형 (task4A)jinmang2/kpfbert86.6694.50
생성형 (task4B)paust/pko-t5-base71.5679.15

단일 실행 기록이므로 일반화된 결론으로 삼을 수는 없지만, 방향은 읽어둘 만하다. 정답이 원문 안에 그대로 있는 문제라면 span을 고르는 쪽이 표기 흔들림 없이 맞히기 유리하다. 생성 방식이 얻는 것은 정확도가 아니라 형식의 통일이다. 2일차 실습5에서는 이 '써내는' 방식이 BERT로는 아예 표현할 수 없는 태스크(수학추론·SQL생성)까지 넓어지는 것을 본다. 정답이 지문 안에 없으면 위치를 찍을 수 없고, 라벨 목록에도 없으면 고를 수도 없다. 그때 남는 방법이 '써내기'다. 생성 방식은 또 디코딩 전략이라는 변수를 새로 갖는다. 1일차 노트북의 T5는 num_beams=1, do_sample=False, 즉 매 자리에서 가장 확률이 높은 토큰만 고르는 greedy로 생성한다(lab_common.generate_t5). 빔서치나 샘플링으로 바꾸면 같은 모델이 다른 답을 낸다.

LLM 시대 — 태스크가 구조에서 프롬프트로 옮겨간다

모델이 커지고 instruction 데이터로 학습되면서, 태스크 구분을 head가 아니라 입력 텍스트가 담게 되었다. 구조가 하나로 유지되므로 여러 태스크를 한 모델에 얹을 수 있고, 이것이 2일차 실습5의 출발점이다.

세 방식을 나란히 놓으면 차이가 분명해진다.

방식태스크 구분이 담기는 곳태스크당 산출물새 태스크 추가
BERT 미세조정모델 구조 (head + num_labels)전체 모델 체크포인트학습 파이프라인을 새로 구성
seq2seq 미세조정입출력 텍스트 형식전체 모델 체크포인트입출력 형식만 재설계
LLM 프롬프트 / instruction입력 텍스트(지시문) 자체없음, 또는 작은 어댑터지시문 추가 또는 데이터 추가

LLM 방식에서 주제분류·개체명인식·기계독해·문장유사도는 전부 "지시문 + 입력 → 텍스트 출력"이라는 하나의 형식으로 표현된다. 모델의 출력층은 여전히 어휘 크기의 LM head 하나뿐이다. 태스크가 늘어도 구조가 늘지 않는다는 점이 BERT 방식과의 결정적 차이다.

대신 새로운 부담이 생긴다.

  • 정답 형식을 모델이 지켜준다는 보장이 없다. 후처리와 형식 검증이 필요하다.
  • 같은 모델을 여러 태스크로 학습시키면 태스크 간 간섭이 생길 수 있다.
  • base 모델이 크므로 전체 미세조정 비용이 크다. 여기서 LoRA 같은 어댑터 방식이 등장한다. base 가중치는 고정하고 작은 행렬만 학습하므로, 태스크가 늘어도 늘어나는 것은 어댑터 몇 MB뿐이다.

2일차와의 연결. 1일차 노트북과 2일차 오전의 기계독해 실습 코드에는 어댑터 관련 코드가 없다. 태스크마다 모델이 하나씩 생기는 구조를 먼저 손으로 겪어보는 것이 그 단계의 목적이다. 2일차 실습5에서는 여섯 태스크를 하나의 LLM + LoRA로 통합 학습해, 방금 표의 마지막 줄이 실제로 어떻게 동작하는지 확인한다. 그리고 같은 데이터·같은 평가셋·같은 채점으로 학습한 BERT(인코더)와 T5(인코더-디코더)를 나란히 놓는다. 인코더(1일차 실습1·2·3과 2일차 실습4A), 인코더-디코더(1일차 T5 파트와 2일차 실습4B), 그리고 2일차 오후의 디코더(실습5) — 셋을 따로 만들어 본 뒤 같은 자로 재보는 순서다.

데이터가 어떻게 생겼는가 — 학습 800건, 평가 300건

학습에 쓰는 것은 800건뿐이다. 적어 보이지만 일부러 이 크기로 맞췄다. 2일차에 LLM이 학습한 것과 똑같은 예제라서, 나중에 BERT·T5·GPT 계열을 한 표에 놓을 수 있다. 평가는 따로 떼어 둔 300건으로 하고 학습에는 절대 쓰지 않는다.

노트북은 두 줄로 데이터를 읽는다.

train_rows = L.load_budget("tc")   # 학습셋 800건 — LLM·T5가 학습한 그 예제들
eval_rows  = L.load_eval("tc")     # 평가셋 300건 — 학습에는 쓰지 않는다
L.check_no_leak(train_rows, eval_rows)

한 줄(row)의 구조는 세 방식이 공유한다.

  • row["input"]["text"] — 뉴스 제목. BERT가 토큰화할 대상이고, T5·GPT 계열에게는 지시문 뒤에 붙는 부분이다.
  • row["raw"]["label"] — 원본 정수 라벨 0~6. BERT 학습에만 쓴다.
  • row["gold"] — 라벨 문자열(예: "IT과학"). 채점은 세 방식 모두 이 문자열로 한다.

같은 데이터를 구조에 따라 다르게 꺼내 쓴다는 점이 중요하다. BERT는 정수를, 생성 모델은 문자열을 본다. 그런데 채점은 문자열로 통일되어 있어서, BERT의 예측도 채점 직전에 문자열로 되돌린다.

왜 하필 800건인가. 세 방식을 나란히 놓으려면 평가셋·채점 함수뿐 아니라 학습 예제 수도 같아야 한다. 그래서 2일차 LLM이 학습한 예제를 그대로 가져와 BERT와 T5에도 먹인다(이것을 budget 모드라고 부른다). 평가 300건은 KLUE-YNAT 공식 validation에서 뽑았고, 학습셋과 겹치는 문장은 미리 제거했다(data/llm-ft/stats.json의 dropped_by_leak). L.check_no_leak이 그것을 노트북에서 한 번 더 확인한다.

BERT는 이 문제를 어떤 head로 푸는가

사전학습된 klue/roberta-base는 문장을 토큰별 벡터로 바꾸는 데까지만 안다. 무엇을 답할지는 모른다. 그래서 몸통 위에 출력이 7개인 선형층(분류 head)을 새로 얹고, 그 부분까지 함께 학습시킨다.

몸통과 head. 인코더는 문장을 읽어 토큰마다 벡터를 만든다. 문장 분류에서는 그중 문장 전체를 대표하는 자리([CLS])의 벡터 하나를 뽑아 작은 출력층에 통과시키고, 라벨 개수만큼의 로짓을 얻는다. 손실은 교차엔트로피다.

그 head를 붙여 주는 클래스가 AutoModelForSequenceClassification이고, 출력 차원을 정하는 인자가 num_labels다. 이 숫자 하나가 곧 정답 공간의 크기다. 사전학습에 없던 층이라 무작위로 초기화되므로, 같은 코드가 같은 점수를 내도록 학습 직전에 L.set_seed(42)로 고정한다.

학습 설정은 task5-llm-ft/bert_baseline.py --mode budget과 같다.

학습 800건이면 강의장 GPU에서 10초 안팎이다. 로그의 loss가 내려가면 배우고 있다는 뜻이다. 뒤의 T5 시연까지 포함해 이 노트북 전체가 강의장 PC에서 0.9분이면 끝난다.

평가는 L.predict_bert → L.evaluate 순서로 간다. predict_bert는 로짓에서 argmax로 라벨 번호를 고른 뒤 라벨 문자열로 바꿔 돌려준다. 그래야 common.score_task라는 하나의 채점 함수에 T5·GPT 계열의 예측과 똑같이 넣을 수 있다.

미션 m-tc — 학생이 채우는 두 가지

노트북 전체에서 비어 있는 것은 셀 하나뿐이다. 그 안에 함수 두 개를 채운다. 하나는 라벨 개수에 맞는 분류 head를 붙인 모델을 만드는 것이고, 하나는 제목을 토큰화하고 정답을 정수 라벨로 붙이는 것이다.

① build_model() — 분류 head를 붙인 모델을 돌려준다. 노트북은 7이라고 직접 적지 말고 len(TC_LABELS)를 쓰라고 요구한다. 라벨 목록이 바뀌면 head 크기가 따라 바뀌어야 하고, 숫자를 손으로 적어 두면 그 연결이 끊기기 때문이다.

② encode_choice(tokenizer, rows, max_len) — 데이터를 모델 입력으로 바꾼다. 제목은 r["input"]["text"]에, 정답 정수 라벨은 r["raw"]["label"]에 있다. 토큰화 결과에 labels를 함께 담아 Dataset으로 돌려주면 된다.

다음 '확인' 셀이 검사하는 것 — 무엇을 맞춰야 하는지가 여기 다 적혀 있다.

  • 예제 8건을 넣으면 결과도 8건인가
  • input_ids와 labels가 모두 있는가
  • labels가 정수이고 0~6 범위 안에 있는가
  • build_model()이 만든 모델의 config.num_labels가 len(TC_LABELS)와 같은가

통과하면 앞 8건의 라벨 번호와 그것을 사람 말로 옮긴 목록이 함께 찍힌다. [3, 0, 5, ...]가 ['생활문화', 'IT과학', '스포츠', ...]로 보이는 순간이 '정수 라벨'이 무엇인지 가장 분명해지는 지점이다.

정답 확인. 미션 셀 바로 위에 객관식 문항 두 개(L.quiz("m-tc-1")·L.quiz("m-tc-2"))가 있다. 보기를 고르면 그 자리에서 맞았는지 알려 주고, 정답을 고르면 해설이 펼쳐진다. 막히면 힌트 보기를 눌러 개념 → 근거자료·검색 링크 → “AI에게 이렇게 물어보세요” 순서로 하나씩 열어 보라. 먼저 15분 동안 직접 채워 본 뒤에 여는 것이 좋다.

T5로 같은 문제를 풀면 무엇이 달라지는가

pko-T5는 head를 바꾸지 않는다. 대신 입력 앞에 지시문을 적어 주고, 답을 글자로 써내게 한다. 그래서 '주제를 고르는' 문제가 '주제 이름을 쓰는' 문제로 바뀐다.

BERT는 7개 후보 중에서 골랐다. paust/pko-t5-base는 지시문을 읽고 답을 써낸다. 태스크가 바뀌어도 모델 구조는 그대로고, 바뀌는 것은 입력에 적어 주는 말이다.

이 실습이 쓰는 지시문은 common.py의 TC_INSTRUCTION 하나뿐이다.

다음 뉴스 제목의 주제를 분류하세요.
'IT과학', '경제', '사회', '생활문화', '세계', '스포츠', '정치' 중 하나만 답하세요.

제목: {text}

2일차에 LLM에게 줄 지시문과 한 글자도 다르지 않다. 같은 문장을 주어야 세 방식을 공정하게 비교할 수 있기 때문에, 지시문과 정답 형식을 TASKS 한 곳에만 두었다.

학습 설정은 에폭 3 · 학습률 3e-4 · 배치 8이다(BERT와 학습률·배치가 다르다). 평가에서는 시간이 더 걸린다 — BERT는 점수가 가장 높은 것을 한 번에 고르지만, T5는 글자를 하나씩 이어 붙여 답을 완성하기 때문이다.

새로 생기는 문제: 형식. T5는 무엇이든 써낼 수 있어서, 일곱 라벨 중 어느 것으로도 읽히지 않는 답이 나올 수 있다. 채점 함수는 그런 건수를 broken_format(형식깨짐)으로 따로 센다. BERT에서는 이 숫자가 구조상 항상 0이다 — 7차원 로짓에서 argmax를 하면 반드시 일곱 중 하나가 나온다. 형식을 지키는 일 자체가 생성 모델에게는 배워야 할 과제라는 것이 이 실습에서 처음 드러나는 지점이다.

읽는 법.

  • 80.00과 82.67은 사실상 같은 값이다(정확도 300건의 표준오차 약 2.5점). 일곱 후보 중 하나를 고르는 문제에서는 구조의 차이가 점수로 나타나지 않는다. 답이 짧고 보기 안에 있으면 써내는 쪽도 불리하지 않다는 뜻이다.
  • 그래도 두 방식이 실패하는 모양은 다르다. T5는 라벨 이름을 어긋나게 쓰면 형식깨짐으로 점수를 잃지만, BERT는 그런 실패가 구조상 불가능하다. 점수가 같다고 성격이 같은 것은 아니다.
  • 학습이 800건뿐이라는 점도 함께 봐야 한다. docs/LECTURE-FACTS.md §4의 별도 스윕에서 같은 두 모델을 공식 학습셋 전체(45,678건)로 학습하면 BERT 84.7 · T5 85.3까지 오른다. 두 구조 모두 아직 데이터가 부족한 상태였다는 뜻이다.
  • 2일차에 만날 LLM은 같은 800건을 학습해 40.7 → 71.7이 된다(LECTURE-FACTS §4, EXAONE-4.0-1.2B). 태스크 하나만 놓고 보면 여전히 BERT·T5 쪽이 높다. LLM의 값어치는 이 한 칸이 아니라 같은 모델 하나로 여섯 태스크를 함께 푼다는 데 있다.

실습2: 문장유사도 (KLUE-STS)

day1/02_문장유사도.ipynb — 두 문장의 의미가 얼마나 비슷한지 0~5 점수로 매긴다. 정답이 후보 중 하나가 아니라 연속된 수라서, 분류 head 대신 회귀 head를 쓴다.

무엇을 푸는가 — 정답이 '후보 중 하나'가 아니다

KLUE-STS는 두 문장에 0~5 사이의 유사도 점수가 붙은 데이터다. 앞의 주제분류와 결정적으로 다른 점은 정답이 고르는 값이 아니라 연속된 수라는 것이다. 그래서 지표도 정확도가 아니라 피어슨 상관을 쓴다.

예시는 이런 모양이다.

문장1: 침사추이쪽에 숙소를 잡으실 분이라면 침사추이 부근 유명지에 접근성은 좋은편입니다.
문장2: 침사추이에 숙박하고 싶다면 침사추이 근처에 있는 유명한 장소를 쉽게 찾을 수 있습니다.
정답: 3.3

정답이 3.3이라는 점을 눈여겨볼 것. 라벨 목록이 없으므로 '맞았다/틀렸다'로 셀 수 없고, 얼마나 가깝게 맞혔는가를 재야 한다.

대표 지표는 피어슨 상관(×100)이다. 모델이 매긴 점수 300개와 사람이 매긴 점수 300개가 같이 오르내리는 정도를 잰다. 값 자체가 조금씩 어긋나도 순서 관계가 맞으면 높게 나온다. 보조로 3.0을 기준으로 '비슷하다/아니다'를 나눈 이진 정확도도 함께 찍는다.

데이터가 어떻게 생겼는가 — 학습 600건, 평가 300건

한 줄에 문장이 둘이고 정답이 실수 하나다. 학습은 600건, 평가는 따로 떼어 둔 300건. 세 태스크 중 학습 예제가 가장 적어서, 뒤에 나올 '시드에 따라 흔들린다'는 이야기가 여기서 가장 크게 나타난다.

 
train_rows = L.load_budget("sts")   # 학습셋 600건
eval_rows  = L.load_eval("sts")     # 평가셋 300건
L.check_no_leak(train_rows, eval_rows)

한 줄의 구조는 이렇다.

  • row["input"]["sentence1"], row["input"]["sentence2"] — 비교할 두 문장
  • row["raw"]["score"] — 원본 점수 0.0~5.0의 실수. BERT 학습에 쓴다.
  • row["gold"] — 채점에 쓰는 정답. 세 방식이 모두 이것과 비교된다.

주제분류에서는 raw가 정수였는데 여기서는 실수다. 정답의 성질이 다르면 라벨의 자료형도 다르다는 것이 이 실습에서 미션의 절반을 차지한다.

평가 300건은 KLUE-STS 공식 validation에서 뽑았고, 학습셋과 겹치는 문장은 미리 뺐다. 학습 600건은 2일차에 LLM이 학습한 바로 그 예제들이라, 세 방식을 같은 조건에서 비교할 수 있다.

BERT는 이 문제를 어떤 head로 푸는가 — 분류가 아니라 회귀

주제분류와 뼈대는 같고 head만 다르다. 출력이 일곱 개인 분류 head 대신 출력이 하나뿐인 회귀 head를 얹고, 손실을 교차엔트로피 대신 MSE(평균제곱오차)로 바꾼다. 입력도 문장 하나가 아니라 문장 쌍이다.

입력: 두 문장을 한 줄로. 토크나이저에 문장 목록을 두 개 넘기면 [CLS] 문장1 [SEP] 문장2 [SEP] 형태로 이어 붙는다. 인코더의 self-attention이 두 문장을 함께 보게 되므로, [CLS] 벡터 하나에 '두 문장의 관계'가 담긴다. 문장을 따로 인코딩해 벡터 거리를 재는 방식과는 다른 접근이다.

출력: 값 하나. 같은 AutoModelForSequenceClassification을 쓰지만 num_labels를 1로 두면 로짓이 하나만 나온다. 여기에 problem_type을 "regression"으로 지정하면 손실이 MSE로 바뀐다 — 예측값과 정답의 차이를 제곱해 평균 낸다. '맞았나 틀렸나'가 아니라 '얼마나 멀리 빗나갔나'를 줄이는 학습이다.

학습 설정. klue/roberta-base · 학습률 5e-5 · 배치 32 · 최대 길이 128까지는 주제분류와 같고, 에폭만 5다(다른 두 실습은 3). 이유는 마지막 카드에서 따로 다룬다. 에폭을 올려도 이 노트북 전체는 강의장 PC에서 0.9분이면 끝난다(추가 비용 약 2초).

평가할 때는 L.predict_bert가 모델이 낸 값을 0~5로 자른 뒤 소수점 한 자리 문자열(예: "3.3")로 바꾼다. T5·GPT 계열이 내놓는 형식과 같게 맞춰야 같은 채점 함수에 넣을 수 있기 때문이다.

미션 m-sts — 학생이 채우는 두 가지

앞의 미션과 모양이 같다. 모델을 만드는 함수 하나, 데이터를 모델 입력으로 바꾸는 함수 하나. 다만 둘 다 '연속된 값'이라는 성질에 맞춰야 한다.

① build_model() — 출력이 하나뿐인 head를 붙이고, 손실이 MSE가 되도록 problem_type을 지정한다. 두 인자가 짝이라는 점이 요점이다. 출력 개수만 1로 줄이고 손실 종류를 말해 주지 않으면 무엇을 최소화해야 하는지가 정해지지 않는다.

② encode_sts(tokenizer, rows, max_len) — 두 문장을 한 쌍으로 토큰화하고, 정답 점수를 실수로 붙인다. 문장은 r["input"]["sentence1"]·r["input"]["sentence2"], 점수는 r["raw"]["score"]에 있다.

다음 '확인' 셀이 검사하는 것.

  • labels가 실수이고 0.0~5.0 범위 안에 있는가 — 정수로 만들면 여기서 걸린다
  • 문장 쌍의 토큰 수가 문장1만 토큰화한 것보다 긴가 — 두 문장을 정말 한 줄로 이어 붙였는지 보는 검사다. 문장1만 토큰화하고 문장2를 빠뜨리는 것이 가장 흔한 실수다.
  • config.num_labels가 1인가
  • config.problem_type이 "regression"인가

통과하면 앞 8건의 정답 점수와, 문장1만 넣었을 때 대비 문장 쌍의 토큰 수가 함께 찍힌다.

정답 확인. 미션 셀 바로 위에 객관식 문항 두 개(L.quiz("m-sts-1")·L.quiz("m-sts-2"))가 있다. 보기를 고르면 그 자리에서 맞았는지 알려 주고, 정답을 고르면 해설이 펼쳐진다. 막히면 힌트 보기를 눌러 개념 → 근거자료·검색 링크 → “AI에게 이렇게 물어보세요” 순서로 하나씩 열어 보라. 먼저 15분 동안 직접 채워 본 뒤에 여는 것이 좋다.

T5로 같은 문제를 풀면 무엇이 달라지는가

T5에게는 회귀 head가 없다. 대신 '3.3' 같은 숫자를 글자로 써낸다. 수를 예측하는 문제가 문자열을 생성하는 문제로 바뀌는 셈이라, 형식이 깨질 여지가 앞의 태스크보다 크다.

지시문은 common.py의 STS_INSTRUCTION 하나다.

다음 두 문장의 의미가 얼마나 비슷한지 0에서 5 사이의 점수로 매기세요.
0은 전혀 다른 의미, 5는 완전히 같은 의미입니다. 소수점 한 자리 숫자만 답하세요.

문장1: {sentence1}
문장2: {sentence2}

마지막 줄이 형식 지시다. 그럼에도 생성 모델은 "약 3점 정도입니다"처럼 쓸 수 있다. 채점 함수는 예측에서 수를 읽어 내지 못하면 그 건을 broken_format으로 세고 중간값 2.5로 채운다 — 무응답이 우연히 유리해지지 않도록 하되, 점수 손해는 그대로 지게 하는 처리다.

BERT에서는 이런 일이 생기지 않는다. 회귀 head의 출력은 애초에 수 하나이고, predict_bert가 0~5로 자른 뒤 소수점 한 자리로 찍어 주기 때문이다. 같은 문제를 풀어도, 답을 담는 그릇이 다르면 실패하는 방식이 달라진다.

학습 설정은 다른 두 실습과 같다 — 에폭 3 · 학습률 3e-4 · 배치 8.

결과 — 그리고 이 노트북만 에폭이 5인 이유

  • 이 격차가 구조의 한계인지 데이터가 적어서인지는 docs/LECTURE-FACTS.md §4의 별도 스윕이 알려 준다. 같은 두 모델을 공식 학습셋 전체(11,668건)로 학습하면 BERT 90.2 · T5 87.7로 둘 다 크게 오르고 격차도 줄어든다. 즉 600건에서의 격차는 데이터가 적을 때 특히 크게 나타나는 차이에 가깝다.
  • 2일차 LLM은 같은 600건으로 13.7 → 80.8이 된다(LECTURE-FACTS §4, EXAONE-4.0-1.2B). 학습 전 13.7은 지시문만 보고 '소수점 한 자리 숫자 하나'라는 형식을 지키기가 어렵다는 뜻이다.

이 노트북만 에폭이 5다. 다른 두 실습은 3인데 여기만 5로 두었다. 회귀 head는 출력이 하나뿐이라 무작위로 시작한 그 값 하나에 결과가 크게 좌우되는데, 학습 예제가 600건이라 그 영향을 씻어낼 시간이 부족하기 때문이다. 에폭 3에서는 초기화 운에 따라 피어슨이 62에서 86 사이로 흔들렸고, 5로 올리자 시드 3개·기계 2대에서 모두 80 이상으로 안정됐다. 추가로 든 시간은 약 2초다. 터미널에서 같은 값을 보려면 bert_baseline.py에 --epochs 5를 붙이면 된다.

실습3: 개체명인식 (KLUE-NER)

day1/03_개체명인식.ipynb — 답이 문장마다 하나가 아니라 토큰마다 하나다. 글자 단위로 붙어 있는 정답을 서브워드 토큰에 맞추는 일이 이 실습의 핵심이고, 미션도 그것 하나다.

무엇을 푸는가 — 문장에서 개체를 모두 찾아내기

한국어 문장에서 사람·지역·기관·날짜·시간·수량 여섯 종류의 개체를 모두 찾아 표시한다. 앞의 두 실습과 다른 점은 답이 문장마다 하나가 아니라 토큰마다 하나라는 것이다. 그래서 문장 분류가 아니라 토큰 분류를 한다.

예시는 이런 모양이다.

문장: 김 씨는 10개월 후에 재검을 받는다는 조건으로 귀가를 통보를 받았다.
정답: [{"text": "김", "label": "PS"}, {"text": "10개월 후", "label": "DT"}]

개체 유형은 여섯 가지다 — PS(사람), LC(지역), OG(기관), DT(날짜), TI(시간), QT(수량).

답이 목록이라는 점이 앞의 두 태스크와 다르다. 개체가 없으면 빈 목록이고, 여럿이면 여럿을 다 찾아야 한다. 그래서 지표도 정확도가 아니라 개체 단위 F1이다 — 몇 개를 맞게 찾았는지(정밀도)와 놓치지 않았는지(재현율)를 함께 본다.

데이터가 어떻게 생겼는가 — 글자마다 붙어 있는 BIO 태그

학습 1,000건, 평가 300건이다. 원본 정답은 개체 목록과 함께 글자 하나하나에 붙은 태그(char_labels)로도 들어 있다. 이 글자 단위 태그가 미션의 출발점이다.

 
train_rows = L.load_budget("ner")   # 학습셋 1,000건
eval_rows  = L.load_eval("ner")     # 평가셋 300건 (KLUE-NER test에서)
L.check_no_leak(train_rows, eval_rows)

한 줄의 구조는 이렇다.

  • row["input"]["text"] — 원문 한 문장
  • row["raw"]["char_labels"] — 글자 하나마다 붙은 태그. "O"·"B-PS"·"I-PS" 같은 문자열이 문장 길이만큼 늘어서 있다.
  • row["gold"] — 채점용 개체 목록 [{"text": ..., "label": ...}]

BIO 표기가 왜 필요한가. '개체다 / 아니다' 두 값만 쓰면 나란히 붙어 있는 두 개체를 나눌 수 없다. B-(begin)로 개체의 시작을, I-(inside)로 이어짐을 표시해야 '김 씨 박 씨'가 하나가 아니라 둘임을 표현할 수 있다. 여섯 유형 각각에 B-·I-가 붙고 여기에 O 하나를 더해 태그는 모두 13개다(L.BIO_LABELS).

평가 300건은 KLUE-NER 공식 test에서 뽑았다(주제분류·문장유사도는 validation). 학습 1,000건은 2일차에 LLM이 학습한 바로 그 예제들이다.

BERT는 이 문제를 어떤 head로 푸는가 — 토큰마다 분류기 하나

문장 하나에 라벨 하나가 아니라, 토큰 하나하나가 각각 13지선다 문제다. 그래서 [CLS] 자리만 쓰는 대신 모든 토큰 위치의 벡터에 같은 분류기를 붙이고, 손실을 토큰마다 계산한다.

출력 모양이 한 차원 늘어난다.

주제분류 · 문장유사도개체명인식
모델 클래스AutoModelForSequenceClassificationAutoModelForTokenClassification
로짓(batch, num_labels)(batch, seq_len, 13)
라벨(batch,)(batch, seq_len)

코드에서 눈에 보이는 차이는 logits.argmax(dim=-1)의 결과가 값 하나가 아니라 토큰 길이만큼의 태그 열이라는 점 하나다. 손실은 토큰마다 계산한 교차엔트로피의 평균이 된다.

이번 실습에서 build_model()은 미션이 아니다. 노트북에 이미 채워져 있고, num_labels=len(L.BIO_LABELS)와 함께 id2label·label2id를 넣어 준다. 앞의 두 실습에서 head를 두 번 만들어 봤으므로, 이번에는 진짜 어려운 부분에 15분을 온전히 쓰게 한 것이다.

학습 설정은 주제분류와 같다 — klue/roberta-base · 에폭 3 · 학습률 5e-5 · 배치 32 · 최대 길이 128. 노트북 전체는 강의장 PC에서 2.0분으로 세 노트북 중 가장 오래 걸린다(T5가 개체 목록을 길게 생성하기 때문이다).

예측을 되돌리는 단계가 하나 더 있다. 모델이 내놓는 것은 토큰별 태그 열인데 채점은 개체 목록으로 한다. 그래서 L.decode_ner이 B-로 시작해 I-가 이어지는 구간을 하나의 개체로 묶고, 토큰의 문자 위치를 이용해 원문에서 그 구간을 잘라낸 뒤, T5·GPT 계열이 내놓는 것과 같은 JSON 문자열로 만든다.

미션 m-ner — 정답이 붙어 있는 단위와 모델이 보는 단위를 맞추기

원본 정답은 글자마다 붙어 있고, 모델이 보는 것은 서브워드 토큰이다. 두 단위가 다르므로 토큰 하나하나에 대해 '이 토큰의 태그는 무엇인가'를 정해 주어야 한다. 규칙은 세 가지이고 위에서부터 순서대로 적용한다.

같은 문장을 두 단위로 보면 이렇게 어긋난다.

글자 단위 정답 : 김(B-PS)  (O) 씨(O) 는(O) 1(B-DT) 0(I-DT) 개(I-DT) …
서브워드 토큰  : [CLS]  김  씨는  10  ##개월  후  에  …  [SEP]

한국어는 조사·어미가 붙어 단어가 길어지기 때문에 토큰 경계가 개체 경계와 자주 어긋난다. 그 둘을 맞추는 것이 이번 미션이다.

어떤 토큰인가라벨
1[CLS]·[SEP] 같은 특수 토큰 (문자 구간이 비어 있다)-100 — 손실 계산에서 뺀다
2시작 글자의 태그가 OO
3시작 글자의 태그가 B-이거나, 앞 토큰과 유형이 다름B-유형 (새 개체의 시작)
3'그 밖 — 앞 토큰과 같은 유형이 이어짐I-유형

-100은 임의의 숫자가 아니다. PyTorch 교차엔트로피의 ignore_index 기본값이라서, 그 자리는 맞히든 틀리든 손실에 아무 영향을 주지 않는다.

토큰과 글자를 잇는 다리. 노트북은 토큰화할 때 return_offsets_mapping=True를 준다. 그러면 토큰마다 '원문의 몇 번째 글자부터 몇 번째까지인가'라는 구간 (s, e)가 함께 나온다. 이 정보가 있어야 char_labels[s]로 그 토큰이 시작하는 글자의 태그를 찾아볼 수 있다. offset은 fast 토크나이저에만 있는 기능이다.

다음 '확인' 셀이 검사하는 것.

  • 라벨 개수가 토큰 개수와 짝이 맞는가 — 하나라도 빠뜨리면 전부 밀린다
  • 문장 앞뒤 특수 토큰의 라벨이 -100인가
  • 모든 라벨이 -100이거나 0~12 범위 안에 있는가
  • 개체가 하나도 표시되지 않은 것은 아닌가 — 전부 O로 채우는 실수를 잡는다
  • I- 앞에 반드시 같은 유형의 B-나 I-가 오는가 — BIO 문법 검사다

통과하면 첫 문장의 토큰과 그에 붙은 태그가 나란히 찍힌다. 서브워드가 어떻게 쪼개졌고 태그가 어디에 붙었는지 눈으로 확인하는 것이 이 미션의 진짜 목적이다.

정답 확인. 미션 셀 바로 위에 객관식 문항 두 개(L.quiz("m-ner-1")·L.quiz("m-ner-2"))가 있다. 보기를 고르면 그 자리에서 맞았는지 알려 주고, 정답을 고르면 해설이 펼쳐진다. 막히면 힌트 보기를 눌러 개념 → 근거자료·검색 링크 → “AI에게 이렇게 물어보세요” 순서로 하나씩 열어 보라. 먼저 15분 동안 직접 채워 본 뒤에 여는 것이 좋다.

T5로 같은 문제를 풀면 무엇이 달라지는가

T5에게는 정렬 작업이 아예 없다. 문장을 읽고 개체 목록을 JSON으로 써낸다. 손이 훨씬 덜 가는 대신, 답이 길고 형식까지 지켜야 해서 세 태스크 중 부담이 가장 크다.

지시문은 common.py의 NER_INSTRUCTION이다.

다음 문장에서 개체명을 모두 찾아 JSON 배열로 출력하세요.
개체명 유형: PS(사람), LC(지역), OG(기관), DT(날짜), TI(시간), QT(수량)
출력 형식: [{"text": "개체명", "label": "유형"}]
개체명이 없으면 [] 를 출력하세요.

문장: {text}

미션에서 30분 가까이 씨름한 글자↔토큰 정렬이 여기서는 통째로 사라진다. BIO도, -100도, offset도 필요 없다. 그 대신 T5가 짊어지는 것이 세 가지다.

  • 대괄호와 따옴표를 정확히 닫아야 한다. 채점 함수는 예측에서 [...]를 찾지 못하면 그 건을 broken_format으로 센다.
  • 개체 문자열을 원문 그대로 옮겨 적어야 한다. 채점은 (텍스트, 유형) 쌍이 정확히 같아야 1건을 인정한다. 조사 한 글자가 더 붙거나 빠지면 그 개체는 틀린 것이 된다. BERT는 원문에서 구간을 잘라내므로 이런 일이 생기지 않는다.
  • 답이 길다. 개체가 여럿이면 그만큼 길게 생성해야 한다(max_new_tokens가 세 태스크 중 가장 크다). 생성이 길수록 어긋날 자리도 늘어난다.

학습 설정은 다른 두 실습과 같다 — 에폭 3 · 학습률 3e-4 · 배치 8.

채점과 결과 — 개체 단위 F1은 부분 점수를 주지 않는다

채점 단위는 토큰이 아니라 개체다. 텍스트와 유형이 모두 맞아야 1건을 인정하고, 경계가 한 글자만 어긋나도 부분 점수가 없다. 그래서 '거의 다 맞힌 것 같은데' 점수가 낮은 일이 자주 생긴다. 노트북 실측은 BERT 79.72, T5 71.21다.

채점 방식. common.score_ner은 예측한 개체들을 (텍스트, 유형) 쌍의 다중집합으로 만들고, 정답 쪽과 겹치는 개수를 센다. 여기서 정밀도(예측한 것 중 맞은 비율)와 재현율(정답 중 찾아낸 비율)을 내고 F1로 합친다.

부분 점수가 없다는 점이 중요하다. 정답이 "10개월 후"인데 "10개월"이라고 예측하면 정답 하나를 놓치고(재현율 손실) 동시에 틀린 개체 하나를 만든 것(정밀도 손실)이 되어 두 번 깎인다. 유형만 어긋나도(OG를 LC로) 마찬가지다.

세 방식이 모두 이 하나의 함수로 채점된다. BERT의 토큰별 태그 열은 L.decode_ner이 개체 목록으로 되돌리고, T5·GPT 계열은 처음부터 목록을 써낸다. 형태만 맞춰 주면 같은 자로 잰다는 것이 이 실습 설계의 핵심이다.

추출형 QA는 정답을 쓰는 게 아니라 위치를 찍는 문제

KorQuAD의 추출형(extractive) QA는 정답이 지문 안에 그대로 들어 있다고 가정한다. 모델은 정답 구간의 시작 토큰과 끝 토큰 위치를 맞히므로, 생성이 아니라 토큰 위치에 대한 분류 문제다. 학습 라벨은 데이터의 문자 오프셋을 토큰 인덱스로 바꿔서 만든다.

데이터 형태. data/korquad/validation.jsonl의 한 줄은 이렇게 생겼다.

{"id": "6548850-0-0",
 "title": "임종석",
 "context": "1989년 2월 15일 여의도 농민 폭력 시위를 주도한 혐의로 지명수배되었다. ...",
 "question": "임종석이 여의도 농민 폭력 시위를 주도한 혐의로 지명수배 된 날은?",
 "answers": {"text": ["1989년 2월 15일"], "answer_start": [0]}}

정답은 문자열 text와 문자 단위 시작 위치 answer_start로만 주어진다. 끝 위치는 answer_start + len(text)로 계산한다.

모델 출력. AutoModelForQuestionAnswering은 입력 토큰마다 start logit과 end logit 두 개를 낸다. 길이 L 시퀀스면 (L,) 벡터가 두 개고, 학습 라벨은 정수 하나씩(start_positions, end_positions)이다.

문자에서 토큰으로. 노트북 4A 에서는 L.encode_mrc_train(§4 미션 셀 ①) 이 이 변환을 한다 — 여러분이 채우는 빈칸이 바로 이 안에 있다. 참고용 스크립트 task4A-qa-ext/train_qa.py의 prepare_train_features()도 같은 일을 한다. 토크나이저를 return_offsets_mapping=True로 부르면 각 토큰이 원문의 어느 문자 구간에서 왔는지 (start_char, end_char)가 나온다. 이 오프셋을 훑으며 정답 문자 구간을 덮는 토큰 인덱스를 찾아 라벨로 붙인다.

또 하나 중요한 것이 sequence_ids(i)다. 입력은 [CLS] 질문 [SEP] 지문 [SEP] 형태이므로 질문 토큰(id 0)과 지문 토큰(id 1)을 구분해야 정답 탐색 범위를 지문으로 한정할 수 있다.

답이 없는 경우. KorQuAD v1은 모든 질문에 답이 있어 version_2_with_negative는 기본 False다. 다만 코드는 SQuAD 2.0식 무답 케이스도 다룰 수 있게 되어 있고, 답이 없으면 [CLS] 위치를 라벨로 쓴다.

긴 지문 처리: 겹치는 창으로 자르기 (doc_stride)

위키백과 문단은 512 토큰을 넘기 일쑤다. 그냥 자르면 정답이 잘려 나가므로 겹치는 창으로 지문을 나눠 여러 개의 입력 feature를 만든다. 그래서 example 개수와 feature 개수가 달라지고, 이 대응 관계를 끝까지 들고 다녀야 한다.

어떻게 나누나. 학습·검증 전처리 모두 아래 형태로 토크나이저를 부른다.

tokenized_examples = tokenizer(
    examples[question_column_name],   # 질문
    examples[context_column_name],    # 지문
    truncation="only_second",         # 질문은 두고 지문만 자른다
    max_length=384,                   # 노트북 4A 의 L.MAX_LEN_MRC
    stride=128,                       # 노트북 4A 의 L.STRIDE_MRC
    return_overflowing_tokens=True,   # 넘친 부분을 버리지 않고 새 feature로
    return_offsets_mapping=True,
    padding="max_length",
)

truncation="only_second"이므로 질문은 온전히 남고 지문만 잘린다. stride=128은 앞 창의 마지막 128 토큰을 다음 창이 다시 포함한다는 뜻이다. 경계에 걸친 정답이 어느 한 창에는 온전히 들어가도록 하는 장치다.

example ↔ feature 대응. 이렇게 하면 example 하나가 feature 여러 개를 만든다. 그 대응표가 overflow_to_sample_mapping이고, 코드는 이걸 sample_mapping으로 꺼내 쓴다. 학습 전처리에서는 정답 문자 구간이 현재 창 밖이면 그 feature는 답이 없는 것으로 보고 CLS 인덱스를 라벨로 준다.

if not (offsets[token_start_index][0] <= start_char
        and offsets[token_end_index][1] >= end_char):
    tokenized_examples["start_positions"].append(cls_index)
    tokenized_examples["end_positions"].append(cls_index)

검증 전처리는 조금 다르다. 노트북의 L.encode_mrc_eval(참고 스크립트의 prepare_validation_features())은 라벨을 만들지 않는 대신 두 가지를 남긴다. (1) 나중에 예측을 원래 질문으로 되모으기 위한 example_id, (2) offset_mapping인데 지문이 아닌 위치는 None으로 덮어쓴다. 후처리에서 질문 영역이나 패딩을 답으로 뽑는 사고를 막기 위해서다.

노트북에서 보이는 숫자. 4A §5 는 학습 예제 800건이 조각 861개, 평가 300건이 조각 314개가 된다고 찍는다 — 늘어난 만큼이 창 분할이다. §8 에서 데이터를 30,000건(공식 train 의 절반)으로 늘리면 조각은 33,788개다.

참고 스크립트의 숫자. train-half.jsonl은 30,000 example인데 train_qa-1.sh의 로그는 train_samples = 31129다. validation.jsonl은 5,774 example인데 eval_samples = 6152다. 늘어난 만큼이 창 분할로 생긴 추가 feature다. 같은 데이터라도 모델마다 값이 조금씩 다른데(kpfbert 6152, klue/bert-base 6155, koelectra 6178), 토크나이저가 달라 토큰 수가 달라지기 때문이다.

로짓을 답 문자열로 되돌리기: 후처리 — 미션 셀 ②가 하는 일

모델이 내놓는 것은 숫자 벡터일 뿐이라 EM/F1을 계산할 수 없다. utils_qa.postprocess_qa_predictions()가 여러 feature의 로짓을 모아 원문에서 실제 부분 문자열을 잘라낸다. 표준 Trainer는 이 단계를 모르므로 후처리 훅이 붙은 QuestionAnsweringTrainer를 쓴다.

후처리가 하는 일 — 노트북 4A 의 미션 셀 ② pick_best_span(미션 m-mrc-3)이 이것이고, §6 평가가 300건 전체에 그 함수를 그대로 쓴다. 참고 스크립트에서는 utils_qa.py의 postprocess_qa_predictions다.

  • 같은 example_id를 가진 feature들을 한 질문으로 모은다 (features_per_example).
  • start/end logit 상위 n_best_size(기본 20)개씩만 후보로 본다. 모든 (start, end) 쌍을 다 보는 것은 낭비다.
  • 말이 안 되는 후보를 버린다. 오프셋이 None인 위치(= 지문 밖), end_index < start_index, 길이가 max_answer_length(기본 30)를 넘는 구간.
  • 남은 후보의 점수를 start_logit + end_logit으로 매기고, 오프셋으로 원문을 잘라 답 문자열을 만든다: pred["text"] = context[offsets[0]:offsets[1]].
  • softmax로 확률을 붙이고, 예측 파일을 저장한다. eval 단계면 eval_predictions.json과 eval_nbest_predictions.json이 --output_dir에 떨어진다.

시작과 끝을 각각 독립적으로 예측하기 때문에 이런 제약이 필요하다는 점을 짚고 넘어가면 좋다. max_answer_length 인자 설명에도 그 이유가 적혀 있다.

조각 로짓과 예제 채점 사이. 모델은 조각(feature)마다 시작·끝 점수를 내지만 채점은 예제(question) 단위다. 그 사이를 잇는 것이 pick_best_span 이다 — 같은 예제의 조각을 모으고(sample_map), 후보를 걸러(off is None · e < s · 길이 상한) 점수 합이 가장 큰 구간을 원문에서 잘라낸다. 학습 중의 검증(§5 표의 '시작·끝 둘 다 맞음')은 이 후처리를 거치지 않은 로짓 위치 정확도이고, §6 의 EM·F1 은 이 후처리를 거친 답 문자열을 common.score_task 로 채점한 값이다 — 둘이 다른 이유다. 퀴즈 q-mrc-3 이 바로 이 지점을 묻는다.

EM과 F1, 그리고 한국어 채점

EM은 정규화 후 정답과 완전히 같아야 1점, F1은 겹치는 정도로 부분점수를 준다. 학습 중에는 evaluate의 squad 지표를 쓰고, 끝난 뒤에는 KorQuAD v1.0 공식 스크립트로 다시 채점한다. 두 F1 값이 다르게 나오는데, 그 이유가 한국어 채점의 핵심이다.

학습 중 지표. 노트북 4A 는 전체 스텝의 1/5마다 검증셋(학습 예제의 10%)으로 시작·끝 둘 다 맞음·시작만(로짓 위치 정확도)을 표에 찍고, 4B(T5)는 같은 간격으로 답을 실제로 생성해 EM·F1 을 찍는다.

최종 채점. §6 에서 300건 평가셋의 답 문자열을 common.score_task로 잰다 — EM(완전 일치)과 글자 단위 F1. 실습5 의 LLM 도 같은 함수로 채점하므로 세 방식을 한 표에 놓을 수 있다. 참고용으로 KorQuAD v1.0 공식 스크립트도 저장소에 있다.

python task4A-qa-ext/evaluate-KorQuAD-v1.py \
       data/korquad/KorQuAD_v1.0_dev.json  예측파일.json

공식 스크립트의 한국어 조정. evaluate-KorQuAD-v1.py는 SQuAD v1.1 스크립트를 바탕으로 하되 두 군데를 바꿨다.

  • normalize_answer()가 한국어 문헌에 흔한 기호 《》〈〉‘’"'()를 지우고 공백을 정리한다.
  • f1_score()가 어절을 다시 문자 단위로 쪼개서 겹침을 센다. 한국어는 조사 때문에 "서울시가"와 "서울시"가 어절 단위로는 완전 불일치가 되는데, 문자 단위로 보면 대부분 겹치므로 부분점수가 합리적으로 나온다.

targets = [answer["text"][0] if len(answer["text"]) > 0 else "" for answer in answers]
labels  = tokenizer(text_target=targets, max_length=max_answer_length, ...)

뺀 것 두 가지, 그리고 그 이유

  • 감성분류(NSMC) — 뺐다. 이전 구성에서 모델 13종의 학습 전 평균이 이미 82.1점이었고 학습 후에는 89.4점이었다. 올라갈 자리가 거의 없어서, 파인튜닝이 무엇을 바꾸는지 보여주기에 좋은 재료가 아니다.
  • 자연어추론(KLUE-NLI) — 뺐다. 남긴 문장유사도(KLUE-STS)와 자리가 겹치는데다, '전제가 참이면 가설도 참인가'는 처음 듣는 사람에게 설명 비용이 크다. 문장유사도는 '두 문장이 얼마나 비슷한가를 0~5점으로'라 설명이 필요 없다. 이전 구성 13종 평균으로 학습 후는 문장유사도 84.4 · 자연어추론 83.1로 사실상 같은데, 학습 전은 47.0 대 58.2로 벌어져 있다. 즉 학습으로 달라지는 폭이 문장유사도 쪽이 훨씬 크다. 학습 전 점수가 음수까지 내려가는 모델도 있다 — 0~5점 척도라는 출력 형식 자체를 모르기 때문이다(EXAONE-4.0-1.2B 13.7→79.9 · kanana-1.5-2.1B-base 12.0→84.6 · Qwen3.5-0.8B-Base -17.6→85.4).

같은 평가셋, 같은 채점 함수 — 비교가 성립하는 조건

세 방식의 점수를 한 표에 놓으려면 재는 자가 같아야 한다. 평가셋 파일도 채점 코드도 공유하고, 학습셋과 겹치는 것은 학습셋에서 뺀다.

학습에 쓴 데이터로 성능을 재면 시험 문제를 미리 보고 시험 보는 셈이다. 학습셋은 공식 train에서, 평가셋은 공식 test/validation에서만 만들고, 입력이 겹치면 학습셋에서 뺀다(평가셋은 공식 그대로 둔다).

저장되는 어댑터 파일은 약 162MB 정도다. 모델 전체를 복사할 필요가 없으므로 태스크별 어댑터를 여러 개 만들어 갈아끼우는 것도 가능하다. 학습 중 GPU 최대 사용량은 17.1GB였다.

BERT·T5 기준선은 LoRA를 쓰지 않고 전체 파라미터를 학습한다. 크기가 작아서 그래도 되기 때문이다. 'LoRA가 더 좋은 방법'이라서가 아니라 모델이 커지면 전체 학습이 불가능해지기 때문에 쓰는 것이다.

BERT·T5 기준선의 'budget' 조건은 LLM과 같은 학습 예제 수다. 크기가 작아 여러 번 볼 수 있으므로 3에폭을 돌린다. 'BERT, 공식 학습셋 전체' 줄은 데이터가 넉넉할 때 어디까지 가는지를 보여주는 참고선이다.

같은 학습 예제 수에서 BERT 대비 LLM의 차이는 주제분류 +3.0 · 개체명인식 -6.9 · 기계독해 +11.3 · 문장유사도 +17.5이다(양수면 LLM이 앞선다). 차이의 방향이 태스크마다 다르다는 점이 핵심이다. 라벨을 고르거나 위치를 찍으면 되는 문제는 작은 인코더가 효율적이고, 사전학습에서 이미 배운 것을 지시문으로 끌어내면 되는 문제는 디코더가 유리하다.

결론은 '어느 구조가 이겼다'가 아니다. 데이터 양 · 추론 속도 · 태스크 개수에 따라 선택이 달라진다는 것을 같은 자로 재서 확인하는 것이 이 카드의 목적이다. BERT는 태스크마다 모델과 head와 후처리가 따로 필요했고, LLM은 지시문만 다르다. 대신 LLM은 추론이 수십 배 느리다.

BERT가 못 하는 두 가지 — 수학추론과 SQL생성

정답이 라벨도 아니고 입력 안의 구간도 아니면, BERT에 붙일 head 자체가 없다. 점수가 낮은 것이 아니라 문제를 표현할 수 없다. T5와 LLM은 답을 글자로 써내므로 같은 문제를 푼다.

앞의 네 태스크는 정답이 라벨 하나이거나 지문 안의 한 구간이었다. 그래서 BERT는 고르기만 하면 됐다. 이 두 태스크는 그렇지 않다.

  • 수학추론(GSM8K-ko) — 정답은 계산 결과다. 문제 지문 어디에도 그 숫자가 없다. '철수가 3개씩 4묶음을 샀다'에서 12는 만들어 내야 나온다.
  • SQL생성(Spider-ko) — 정답은 SELECT ... FROM ... WHERE ... 같은 문장이다. 질문에도 스키마에도 그 문장은 통째로 들어 있지 않다.

BERT에 붙일 수 있는 head는 '라벨 고르기'와 '위치 찍기'뿐이다. 정답이 그 둘 중 어느 것도 아니면 붙일 head 자체가 없다. 성능이 낮은 것이 아니라 문제를 표현할 수 없다. 반대로 T5는 인코더로 읽고 디코더로 써내기 때문에 같은 문제를 풀 수 있다. LLM도 마찬가지다. 이 두 칸이 비어 있다는 사실이, 세 구조의 차이를 가장 짧게 보여준다.

입력에 없는 것을 만들어 내기 — SQL생성이 보여주는 것

학습 전 모델은 완전일치가 바닥인데 토큰 F1은 절반쯤 나온다. 테이블과 컬럼은 대체로 맞게 골랐는데 문장이 정답과 글자까지 같지는 않다는 뜻이다. 파인튜닝이 채우는 것이 무엇인지가 여기서 가장 잘 보인다.

SQL생성은 두 가지 지표로 함께 본다. 완전일치는 정규화 후 글자까지 같아야 1점이고, 토큰 F1은 SQL을 토큰으로 쪼개 겹치는 정도를 센다.

학습 전 모델은 완전일치 17.0%인데 토큰 F1은 69.3이다. 이 간극이 이 카드의 요점이다. 테이블 이름도 컬럼 이름도 대체로 맞게 골랐다. 그런데 정답과 글자까지 같은 것은 17.0%뿐이다. 별칭을 붙이는 방식, 조건의 순서, 대소문자, 조인을 쓸지 서브쿼리를 쓸지 — 이 데이터셋이 정답으로 삼는 표면 규약을 모르기 때문이다.

학습 뒤에는 완전일치가 17.0 → 35.3로 올라간다. 없던 SQL 지식이 생긴 것이 아니라, 800건을 보면서 이 데이터셋이 어떤 모양의 답을 정답으로 치는지를 배운 것이다. 파인튜닝이 실제로 가르치는 것은 대체로 능력 그 자체보다 그 태스크의 기준과 출력 형식이라는, 앞 카드들과 같은 이야기가 여기서 가장 선명하게 보인다.

완전일치는 실행 결과를 비교하지 않는다. 뜻이 같아도 표면이 다르면 0점이다. 그래서 이 점수는 'SQL을 얼마나 잘 쓰는가'가 아니라 '이 데이터셋의 답안 형식을 얼마나 익혔는가'로 읽어야 한다. 지표가 무엇을 재는지 확인하는 습관이 수치를 읽는 첫 단계다.

모델은 어디서 오나 — Hugging Face 와 모델 카드

코드에는 저장소 주소 한 줄만 있고 나머지는 허깅페이스가 한다. 모델 카드에서 무엇을 보아야 하는지 — 라이선스·접근 조건·크기·문맥 길이·베이스 모델·벤치마크 — 를 실습5 모델로 짚는다. 이 과정의 모델은 전부 공개라 로그인·토큰이 필요 없고, gated 모델을 쓸 때의 절차만 따로 적었다.

이 저장소의 코드에는 모델 파일 경로가 없다. 저장소 주소 하나뿐이다 — MODEL_ID = "skt/A.X-4.0-Light". from_pretrained 가 허깅페이스에서 내려받아 ~/.cache/huggingface/hub 에 두고, 한 번 받은 뒤에는 다시 받지 않는다. 모델을 바꾸는 것은 이 한 줄을 바꾸는 일이다.

모델을 바꾸는 것은 --model 인자 하나다. 지시문도 학습 코드도 평가 코드도 그대로 쓴다. BERT 방식에서 모델을 바꾸려면 태스크 6개를 각각 다시 학습해야 했다는 점과 비교해 보면 좋다.

손실을 어디에 걸 것인가 — 답변 부분에만

학습 데이터 한 건은 [지시문 + 입력 + 답변]이다. 손실을 답변 토큰에만 걸지, 전체에 걸지에 따라 점수가 눈에 띄게 달라진다. 한 번에 한 가지만 바꿔 확인한 실험이다.

SFT 학습 데이터 한 건은 [지시문 + 입력 + 답변]이다. 손실을 답변 토큰에만 걸면 모델은 '답하는 법'만 배우고, 전체에 걸면 지시문·입력을 따라 쓰는 법까지 배운다. TRL SFTConfig(assistant_only_loss=True)가 이 일을 한다 — 단, chat template에 답변 구간 표시({% generation %})가 있어야 쓸 수 있다.

다른 조건은 그대로 두고 이것만 바꿔 다시 학습한 결과다 (train.py --plain-template / --full-loss).

사례 연구 — 멈추지 못하는 모델

기계독해 0점의 원인은 능력이 아니라 종료 토큰이었다. 학습되지 않은 종료 토큰과 이름이 다른 종료 토큰, 두 가지를 어떻게 찾아내고 고쳤는지의 기록이다.

스윕 중 몇몇 모델이 기계독해에서 0점을 받았다. 능력이 없어서가 아니라 답을 쓴 뒤 멈추지 못했기 때문이다. 원인은 두 가지였다.

사례 A — 학습되지 않은 종료 토큰. Mi:dm-2.0-Mini의 chat template은 턴 끝에 <|eot_id|>를 붙인다. 그런데 이 토큰의 출력 임베딩 행이 다른 미사용 특수 토큰과 완전히 같았다 — 사전학습에서 한 번도 학습되지 않았다는 뜻이다. 모델은 이 토큰을 낼 수 없으니 답을 쓴 뒤 계속 이어 쓴다. kanana-1.5-2.1B-base도 마찬가지였다. 해결: common.check_end_token이 임베딩 행을 비교해 학습된 토큰으로 바꾸거나, 단순 형식으로 대체한다.

사례 B — 이름이 다른 종료 토큰. Gemma-4는 <eos>가 아니라 <turn|>(id 106)으로 턴을 끝낸다. 종료 토큰 이름을 코드에 박아 두면 이것을 놓친다. 해결: common.stop_token_ids가 (1) tokenizer의 eos, (2) 템플릿이 실제로 붙이는 마지막 토큰, (3) generation_config의 eos를 합쳐서 종료 조건으로 쓴다.

자기가 학습시킨 모델에 직접 물어보기

Flask로 로컬 데모 페이지를 띄운다. 어댑터를 껐다 켜면서 학습 전 답과 학습 후 답을 나란히 보여주므로, 같은 질문에 답이 어떻게 달라지는지 직접 확인할 수 있다.

 
python task5-llm-ft/serve.py --adapter output/llm-ft --port 9005

브라우저에서 http://localhost:9005 로 접속한다. 여섯 태스크 탭이 있고, 외부 서비스(ngrok, Colab 터널 등)는 필요 없다.

구현상의 요령 — 모델을 두 개 올리면 메모리가 두 배로 든다. 대신 PEFT의 disable_adapter()를 쓰면 어댑터만 잠깐 꺼서 학습 전 모델처럼 동작시킬 수 있다.

after = generate(prompt)              # 어댑터 켜짐 = 학습 후
with model.disable_adapter():
    before = generate(prompt)         # 어댑터 꺼짐 = 학습 전

지난 과정 실습의 serve 단계와 같은 구조다. 특히 SQL생성과 수학추론 탭에서 학습 전 답과 학습 후 답을 나란히 보면, 앞 카드들의 표가 무슨 뜻이었는지 눈으로 확인된다.

맥(Apple Silicon)에서도 되는가 — 같은 코드, 속도만 다르다
